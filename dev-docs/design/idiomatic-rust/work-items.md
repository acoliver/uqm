# Work items: the migration as GitHub issues

This file breaks [plan.md](plan.md) into 63 work units. Each unit is one GitHub issue
and one PR that a single agent can finish and land with every CI job green.
Implementing agents read [AGENTS.md](AGENTS.md) first, then their unit's issue.

work-items.yaml holds the same data and is the input for creating
the issues; it is not committed. Once the issues exist they are the source of truth,
and this file is the readable record of the plan they were created from. Before the
issues are created, architecture.md, quality-gates.md, plan.md, AGENTS.md,
overview.html and this file are committed under `dev-docs/design/idiomatic-rust/`,
the path every issue cites under "Read first".

## Structure

- **One epic** (`IR`): the summary and a checklist of the phase issues.
- **Nine phase issues** (`P0`..`P8`): exit criteria and a checklist of their units. A
  phase closes when all its units have merged and its exit criteria hold on `main`.
- **63 unit issues** (`P<phase>-<nn>`): scope, files, change, out of scope,
  acceptance commands, exit numbers and risks. Units are sized at 500 to 3,000
  changed lines; mechanical moves and deletions may be larger. Each unit leaves
  `main` building, passing every CI job and playable. No unit deletes a
  representation before all of its consumers have moved, and no unit relies on a
  later one to be correct.

Rules that hold for every unit are in [AGENTS.md](AGENTS.md) and are not repeated per
unit: no behaviour change, no weakened assertion, no new global, goldens created
only by P0-08 and changed only by owner-labelled fixes, old path deleted in the same
PR, gate counters only fall, transitional `unsafe` only as AGENTS.md allows.

## Dependency graph: waves and critical path

**Shared-file rule** (the full text is in AGENTS.md). A unit reserves its `touches`
paths while it is in progress; a directory entry covers everything below it. Its
`shared` paths are registries, dispatchers and tables where each unit edits only its
own entries (for example `src/ships/code_resources.rs`, `src/ships/hook_registry.rs`,
`xtask/src/lib.rs`). Two units may be in progress together unless one's `touches`
overlaps the other's `touches` or `shared`. Units that hold the same shared path merge
one at a time: after the first merges, the second rebases on `main` and reruns its
acceptance. `rust/xtask/quality-baseline.toml` is shared by every unit and is
regenerated by xtask after a rebase, never merged by hand.

**Waves.** A wave lists units that can be in progress at once under that rule: every
dependency has merged in an earlier wave, no reservation overlaps, and at most five
worktrees exist. Units are placed in order of their longest remaining dependency
chain. "Shared" lists pairs that hold a common shared path and so merge in sequence.

## Labels

| Label | Meaning |
|---|---|
| `idiomatic-rust` | Idiomatic Rust migration (epic, phases and units) |
| `epic` | Parent roadmap and roll-up issue |
| `ir-phase` | One phase of the migration |
| `ir-unit` | One work unit, landed as one PR |
| `phase-0` .. `phase-8` | The unit's phase |
| `kind-tooling` | xtask, CI or harness code |
| `kind-semantic` | Changes how code works; V1 traces must stay identical |
| `kind-mechanical` | Moves, renames, accessor swaps or dead-code deletion |
| `critical-path` | On the critical path above |
| `owner-review` | Needs the owner's approval before merge (P0-08, P1-01, P1-02, P1-04) |
| `in-progress` | An agent has claimed this unit |
| `blocked` | Stopped; see the linked issue |
| `quality-growth-approved` | Owner only: approves baseline growth |
| `parity-golden-update` | Owner only: a behaviour fix that changes existing goldens |

Every unit issue carries `idiomatic-rust`, `ir-unit`, `phase-<n>` and `kind-<kind>`,
plus `critical-path` and `owner-review` where they apply. Agents set `in-progress`
and `blocked`; they never apply `quality-growth-approved` or `parity-golden-update`.

## Issue bodies

Each unit issue holds `<!-- ir:{id} -->` as its stable key, links to the epic and its
phase, its dependencies as issue links, "Read first: AGENTS.md, then {refs}", and the
sections of its entry below. Every check bundle named in Acceptance is expanded into
its commands with `{unit}` replaced by the unit id, and the V4 block is copied as
written, so an issue states its complete acceptance set. The issue ends with:

```markdown
### Done when
- [ ] one PR titled `{id}: {title}` merged with every CI job green
- [ ] exit numbers reported (base and PR values); no existing golden changed; old path deleted in the same PR
```

Phase issues hold `<!-- ir:P{n} -->`, the exit criteria and a checklist of unit
issues; the epic holds `<!-- ir:IR -->`, the summary and a checklist of phase issues.
Issues are created in dependency order so that every "Depends on" link resolves.

## Check bundles

Commands run from the repository root; `{unit}` is the unit id. `S0` is CI before
P0-04 merges, `S` from P0-04 until P8-01, `S8` from P8-01 (after `abi-check` is
deleted). `P` exists from P0-08 and `V3` in full from P0-08. A unit with no dependency
on P0-04 lists "S0 or S" and runs the one `main` uses when its PR opens. Native runs
(`V2`, `V4`) need macOS; a unit that cannot run them locally relies on the
`failure-scenarios` job for `V2` and says so in the PR. `V4` galleries are inspected
with the image-comparer, not by file size.
